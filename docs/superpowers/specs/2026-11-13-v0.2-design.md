# Dove 0.2 design: permissions, organize, watchers, mail intelligence, Tailscale

Status: approved by the owner on 2026-11-13. Target release: v0.2.0 (new grants, new tools, schema migrations).
This document is the contract the parallel work packages share. Where it and the code disagree, raise it; do not
silently diverge.

## 1. Permissions (grants) and presets

Grants stay per token and per mailbox. New actions next to `read`, `draft`, `send`:

| Action | Allows | Needs | Default in presets |
| --- | --- | --- | --- |
| `read` | search, read, attachments, contacts, digest, watches | - | all presets |
| `draft` | create/update/delete own drafts | `read` | `drafter`, `assistant`, `full` |
| `organize` | mark read/unread, flag/unflag, Gmail labels add/remove, move between folders, archive | `read` | `assistant`, `full` |
| `delete` | move messages to Trash (recoverable). Never permanent deletion, never expunge of anything but Dove's own drafts and a completed move | `organize` | `full` only |
| `send` | `send_draft` (still also needs `allow_send = true` on the instance) | `draft` | none; always explicit |

- Presets: `reader` = read; `drafter` = read,draft; `assistant` = read,draft,organize; `full` = read,draft,organize,delete.
  `send` is never part of a preset, it must be added explicitly (`work=full,send`).
- CLI: `--grant work=assistant`, `--grant work=read,draft,organize`, mixed `--grant work=assistant,send`. Unknown words
  are an error. Stored form stays the expanded action list (presets are input sugar, not stored), so changing a preset
  later never silently widens existing tokens.
- OAuth approval page: per mailbox a preset selector plus checkboxes; `organize` pre-checked (owner decision: organize is
  harmless without delete), `delete` and `send` unchecked. `send` is shown only when `allow_send = true`.
- Rationale for the owner's question "delete and send off by default": organize is reversible and does not destroy
  data, so it is on in the default preset. Delete moves to Trash only (reversible until the provider empties Trash), but
  a steered agent could hide mail from you, so it is opt-in. Permanent deletion is not offered at all: no tool, no
  grant. Send stays behind two gates.
- Moving into the Trash or Spam/Junk folder counts as `delete` (Spam because providers auto-purge it). Moving out of
  Trash/Spam is `organize`.
- Gmail: organize and delete need the `gmail.modify` scope. New connects request `gmail.readonly gmail.compose
  gmail.modify`; existing Gmail mailboxes keep working for read/draft/send and return a clear `reauth_required`-style
  error for organize/delete until `dove accounts reconnect`. Gateway allowlist gains exactly `POST
  users/me/messages/{id}/modify`, `POST users/me/messages/batchModify`, `POST users/me/messages/{id}/trash`,
  `POST users/me/messages/{id}/untrash`, `POST users/me/threads/{id}/modify`. Never `DELETE`, never `batchDelete`.
- IMAP: flags via `UID STORE` (+/-FLAGS `\Seen`, `\Flagged`, keywords), move via `UID MOVE` (RFC 6851) or, without MOVE,
  `UID COPY` + `UID STORE +FLAGS (\Deleted)` + `UID EXPUNGE <that uid>` (UIDPLUS, already required). The `\Deleted`
  step on a non-draft message is allowed only through a new typed guard (like `OwnDraftUid`) that can be constructed
  only from a successful COPY whose COPYUID response confirmed the copy. A source scan test enforces the single
  constructor caller, like the drafts guard.

## 2. Organize tools

- `update_messages(account, ids[], add_flags?, remove_flags?, add_labels?, remove_labels?)` - flags are the
  Gmail-style system labels already used (`UNREAD`, `STARRED`) plus user keywords/labels. At most 100 ids per call.
- `move_messages(account, ids[], to)` where `to` is a folder/label name, or `archive` / `inbox` / `trash`. Trash
  requires `delete`.
- Both are write tools: detached (`tools::detached`), `cx.commit()` before the first side effect, one audit record per
  call with counts, never subjects or addresses. Results report per-id success and new ids (IMAP ids change on move).
- Draft deletion for owned drafts already exists internally; expose `delete_draft(account, draft_id)` for own drafts
  under `draft` (the owner allowed deleting Dove's own drafts).

## 3. Watchers

- `create_watch(account, kind, ...)`, `list_watches()`, `delete_watch(watch_id)`, `list_watch_events(cursor?,
  watch_id?, limit?)`. Watches belong to the token (client) that created them; other tokens never see them.
- Kinds: `thread_reply` (a new message in thread X from someone other than the mailbox owner), `from` (new mail from an
  address or domain), `query` (new mail matching a typed search, same schema as `search_messages`, evaluated on newly
  indexed messages only), `no_reply_by` (thread X gets no reply from others before a deadline; fires once at the
  deadline). Optional `expires_at`; default expiry 30 days, maximum 180 days. At most 50 active watches per client.
- Events are produced by the sync engine when new messages are committed to the index (IMAP IDLE and polling, Gmail
  history sync), and by a scheduler tick for `no_reply_by`. Event payload: watch id, kind, account alias, message id,
  thread id, received_at. No subject, sender or body: the agent reads those through normal tools with its token.
- Delivery: always pull (`list_watch_events`, opaque cursor, events kept 14 days). Optional push: a watch may name a
  **sink** by name. Sinks are created only by the operator (`dove sinks add <name> --url https://... --secret-file`,
  admin socket) and listed to agents by name only. Push = HTTPS POST of the same content-free payload, HMAC-SHA256
  signature header over timestamp + body, bounded retries with backoff, outbound only through the gateway with the
  sink hosts added to the allowlist at runtime from the operator's sink list. Agents can never supply a URL.
- Watches stop when the token is revoked, loses `read` on that mailbox, or the mailbox is removed.

## 4. Mail intelligence (index based, all under `read`)

- `search_contacts(query?, account?, limit?)`: people you exchanged mail with, from the index's address rows: address,
  display name, counts sent/received, first and last contact. Ranked by recency and frequency. Excludes no-reply
  style addresses unless asked.
- `digest(since, accounts?, folders? = inbox, category?)`: compact overview grouped by thread: thread id, subject,
  participants, count, newest received_at, unread, category, a short snippet (bounded, sanitized, inside the
  untrusted-content envelope). Pagination by cursor.
- Category per message at ingest: `personal`, `newsletter` (List-Unsubscribe/List-Id), `notification`
  (Auto-Submitted, Precedence bulk/list/junk, no-reply senders), `calendar` (text/calendar part). Filter in
  `search_messages` and `digest`. Index migration with a rebuild of affected rows or generations.
- Calendar: a `text/calendar` part is parsed into `calendar: {method, summary, start, end, location, organizer,
  attendees_count, uid}` in `get_message` (no attendee addresses beyond the organizer, bounded sizes).
- Attachment text: PDF, DOCX, ODT, plain text and CSV attachments up to a size cap are converted to text at ingest and
  indexed (attachment text is searchable with a flag `in: attachments` or included in `text`), and `get_attachment`
  gains `as_text: true`. Extraction runs with time and memory bounds and never executes content.

## 5. Sending identities and signatures

- IMAP send-as aliases: `dove accounts aliases add <alias> <address> [--name]` (admin). `create_draft.from` accepts
  the mailbox address or a configured alias; anything else is `invalid_argument`. The SMTP envelope sender stays the
  login address unless the alias is marked envelope-capable.
- Signatures: per mailbox (and per alias) a plain-text signature set by the operator (`dove accounts signature set
  <alias> --file`). `create_draft` appends it after the body (before the quote) unless `signature: false`.

## 6. Tailscale

- `dove tailscale setup`: reads the node's MagicDNS name from `tailscale status --json`, writes `public_url`
  (with port), and configures `tailscale serve` with exactly Dove's public path allowlist; idempotent; `--funnel` only
  on explicit request with a warning. `dove doctor` checks the serve config matches.
- Tailnet identity binding is optional and only if Dove can trust it: `tailscale serve` sets `Tailscale-User-Login`
  headers but any local process can reach Dove's loopback port with forged headers. Only implement binding if the
  identity can be verified (for example via the tailscaled LocalAPI `whois` on the peer address, or serve to a Unix
  socket only tailscaled can reach); otherwise document why it is left out.

## 7. Shared conventions for the work packages

- Migrations: append new entries to `MIGRATIONS` (state store `src/store/schema.rs`, index `src/index/schema.rs`)
  with descriptive constant names (`V_WATCHES`, not `V4`). Do not hardcode schema version numbers in tests; the
  coordinator concatenates migrations from several branches at merge time.
- Every new tool: registered in `src/tools/mod.rs`, goes through `policy::authorize` with the right capability, one
  audit record, unknown/out-of-scope ids `not_found`, tool annotations (`readOnlyHint`, `destructiveHint`) set.
- Update docs you own (sections named in your task), add AGENTS.md learnings, CHANGELOG `## [Unreleased]` entries.
- Tests: write the test, break the code to see it fail, then fix. Fake IMAP/Google servers in `tests/support/`.
